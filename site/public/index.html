Setting up the server is one line too.

  1. vpsa fresh server, one agent on it

    Start from an empty server.

    Install any coding agent on a new VPS and give it one line. It reads the setup guide from huta.run and works from there.

    Set this server up for huta. Follow https://huta.run/host.md
  2. agentsurveying the plot

    It looks before it touches anything.

    A read-only pass first: architecture, virtualization, cgroups, loop devices, Python, open ports, firewall, ssh. A blocker stops it, with the reason.

    x86_64 ✓ · kvm ✓ · cgroup2 ✓ · loop ✓
  3. youat the safe

    You answer, and type the keys yourself.

    Your domains, a name for the host, your tailnet. The GitHub and Cloudflare tokens go in at a hidden prompt in your own session; the agent never sees them. Then Docker, Caddy and Tailscale go down as the ground.

    GITHUB_TOKEN set · Cloudflare token active
  4. agentat the fence

    Walls go up with a way back.

    Every firewall and ssh change is applied with a five-minute undo, and stays only once your new login works. Nobody gets locked out.

    nft -c ✓ · sshd -t ✓ · new session ✓ · undo cancelled
  5. hostready for releases

    Then huta moves in.

    Installed from a commit you have seen, containers fenced off behind the egress guard, and a registry and an ssh door on the tailnet for your dev boxes. Each of those then runs install.md.

    huta check · registry ok · huta edge myapp prod --apply

Traffic never moved. What was live keeps serving.

What exists today

Running in production on one server. Anything not listed as available does not exist yet.

  • One HTTP container per project, on two slots
  • Secrets and settings from the server; a dev box can send a secret's value, which goes live with the next approved release
  • Outbound HTTPS by hostname allowlist, and named host services; no DNS or route out otherwise
  • A data volume per target, consistent backups shipped off the server, import and export on the server
  • Scheduled jobs in the live release's image
  • Smoke checks before the switch, public checks after it, automatic switch back
  • Taking over a live site without a gap
  • From a dev box on the same server (pull), or from any enrolled machine (push)
  • One-tap Deploy and Reject in Telegram, owner only; huta approve on the server always works
  • Read-only debugging for agents: status, log, jobs, logs, egress-log, traffic, crashes, diag
  • Caddy as the edge with generated vhosts, Cloudflare Origin CA certificates
  • Crash recovery with huta reconcile; rollback as an approved plan
  • Several containers per target: a slot is the whole set, workers hand over after the switch
  • Postgres per target, run by huta; schema migrations with restore points and restore plans
  • Gateways for services huta doesn't run; publishing to Cloudflare Pages and Workers

Planned, not built:

  • huta snapshot: a sanitized copy of data for debugging
  • Unattended releases
  • Monitoring hooks; TLS without Cloudflare
